## What you'll learn

New ClickHouse users often run into the same set of pitfalls — from accumulating too many data parts to picking the wrong primary key.
This quickstart walks you through the thirteen most common mistakes, explains why they happen, and shows you how to fix or avoid each one.
By the end you'll be able to diagnose these issues in your own deployments and apply best-practice patterns from day one.

<Steps titleSize="h3">

    <Step>
        ### Too many parts

        Every `INSERT` into a MergeTree table creates a new **data part** on disk. If parts accumulate faster than ClickHouse can merge them, queries slow down and you may see the error `Too many parts`.

        The three most common causes are:

        | Cause | Why it's a problem |
        |---|---|
        | High-cardinality partition keys | Using a column like a millisecond timestamp as `PARTITION BY` creates thousands of partitions. Parts in different partitions are never merged together. |
        | Small, frequent inserts | Each `INSERT` creates a separate part. Inserting one row at a time produces thousands of tiny parts. |
        | Too many materialized views | Each view attached to a table generates its own parts on every insert, multiplying the problem. |

        Check how many active parts your table has:

        ```sql
        SELECT
            table,
            count() AS parts,
            sum(rows) AS total_rows
        FROM system.parts
        WHERE active AND database = currentDatabase()
        GROUP BY table
        ORDER BY parts DESC;
        ```

        **How to fix it:**

        - Choose partition keys with fewer than 1,000 distinct values — `toYYYYMM(date)` is a safe default.
        - Batch inserts client-side to at least 1,000 rows per `INSERT`, or enable [async inserts](/docs/en/cloud/bestpractices/asynchronous-inserts) to let the server buffer for you.
        - Consolidate materialized views where possible.
    </Step>

    <Step>
        ### Going horizontal too early

        ClickHouse is engineered to saturate a single machine's resources. Unlike JVM-based databases with heap limitations, ClickHouse efficiently uses hundreds of cores, terabytes of RAM, and petabyte-scale storage on one server.

        Before adding shards, consider:

        - **Lower operational overhead** — fewer nodes means simpler monitoring, upgrades, and backups.
        - **Better join performance** — joins across shards are expensive; keeping data on one node avoids distributed shuffles.
        - **Cost efficiency** — one large machine is often cheaper than several small ones.

        Two replicas on large machines typically provide the redundancy and performance most workloads need. Only distribute data when you've genuinely exhausted vertical scaling.

        <Tip>
        ClickHouse Cloud handles autoscaling for you — it automatically adjusts compute resources based on your workload, so you can scale vertically without manual intervention.
        </Tip>
    </Step>

    <Step>
        ### Mutation pain

        `ALTER TABLE ... UPDATE` and `ALTER TABLE ... DELETE` statements trigger **mutations** — heavy operations that rewrite entire data parts. Mutations compete with background merges for thread-pool resources, must propagate across all replicas, and cannot be rolled back — only cancelled. Excessive mutations can cascade into "too many parts" errors and replication lag.

        Check for running or queued mutations:

        ```sql
        SELECT
            table,
            command,
            create_time,
            is_done
        FROM system.mutations
        WHERE database = currentDatabase()
        ORDER BY create_time DESC
        LIMIT 10;
        ```

        **Alternatives to mutations:**

        - Deduplicate at ingestion time instead of deleting duplicates after the fact.
        - Use the `ReplacingMergeTree` engine, which collapses duplicate rows during background merges (with the caveat that merging is non-deterministic in timing).
        - Use query-time deduplication with `argMax` to always pick the latest version of a row.
        - Use [lightweight deletes](/docs/en/sql-reference/statements/delete) (`DELETE FROM`) instead of `ALTER TABLE ... DELETE` — they mark rows as deleted without rewriting parts.
    </Step>

    <Step>
        ### Unnecessary complex types

        Rich types like `Nested`, `Tuple`, `Map`, and `JSON` are powerful but sacrifice performance when simpler alternatives exist. Where the schema is known ahead of time, prefer explicit flat columns.

        **JSON-specific concerns:**

        - Dynamic schema inference adds overhead at insert time.
        - JSON columns cannot use codecs and generate unnecessary `Nullable` sub-columns.
        - JSON columns cannot be used in primary keys.
        - Reserve JSON for genuinely dynamic data such as Kubernetes labels or user-defined metadata.

        **Nullable overhead:** Every `Nullable` column stores an extra `UInt8` mask column. If a column is never actually null, define it as non-nullable to save storage and improve query speed.

        **Guidance:** Explicitly specify your schema when the schema is known.
    </Step>

    <Step>
        ### Deduplication at insert time

        If you insert the same block of data twice into a **replicated** table, the second insert appears to succeed but no new rows appear. This is not a bug — it's a safety feature.

        ClickHouse hashes each inserted block and stores the hash in a deduplication window (default: 100 blocks). If an identical block is inserted again, it is silently skipped. This enables safe retries after network failures.

        The setting `replicated_deduplication_window` controls the window size. Larger values protect against more retries but slow down inserts because more hashes must be compared.

        For non-replicated tables, the equivalent setting is `non_replicated_deduplication_window`.

        <Warning>
        If you are loading test data and re-running the same INSERT, deduplication may silently drop your rows. Vary your test data or temporarily set `replicated_deduplication_window = 0` during development.
        </Warning>
    </Step>

    <Step>
        ### Poor primary key selection

        ClickHouse uses a **sparse index** — it stores one index entry per granule (default 8,192 rows), not one entry per row. The index identifies which groups of rows *might* match your query, then ClickHouse scans only those groups.

        For this to work well:

        1. **Order columns by ascending cardinality.** Place low-cardinality columns first (e.g., `region` before `user_id`) so the index can skip the most data.
        2. **Use 2–3 frequently filtered columns.** Adding more columns to `ORDER BY` rarely helps the index but increases write amplification.
        3. **Don't expect point lookups.** ClickHouse's sparse index is optimised for analytical range scans, not single-row OLTP lookups.

        Verify how much data your queries actually read:

        ```sql
        SELECT
            query,
            read_rows,
            read_bytes,
            result_rows
        FROM system.query_log
        WHERE type = 'QueryFinish'
            AND query LIKE '%your_table%'
        ORDER BY event_time DESC
        LIMIT 5;
        ```

        If `read_rows` is much larger than `result_rows`, your primary key may not match your query patterns.
    </Step>

    <Step>
        ### Overuse of data skipping indices

        Data skipping indices (e.g., `INDEX idx expr TYPE minmax GRANULARITY 4`) are secondary indices that let ClickHouse skip blocks where the `WHERE` condition cannot match. They sound appealing but are easy to misuse.

        **When they help:** Only when there is a strong correlation between the primary key order and the indexed column. For example, if data arrives roughly in timestamp order and you add a `minmax` index on `event_type`, each block likely contains only a few event types, so the index can skip effectively.

        **When they hurt:** If the indexed column values are randomly distributed across blocks, the index matches almost every block. You still pay the insert-time cost of maintaining the index with no query-time benefit.

        **Try these alternatives first:**

        - Adjust your primary key to cover the filtered column.
        - Create a [projection](/docs/get-started/quickstarts/create-your-first-projection) or [materialized view](/docs/get-started/quickstarts/create-your-first-materialized-view) with a different sort order.
    </Step>

    <Step>
        ### LIMIT doesn't always short circuit

        `LIMIT` does not always stop ClickHouse from reading the full dataset.

        **Streaming (fast):** A simple `SELECT * FROM table LIMIT 10` reads only the first few granules — this is very fast.

        **Non-streaming (full scan):** If the query includes `ORDER BY` on a column that is *not* part of the table's primary key, ClickHouse must scan the entire table to find the top-N results:

        ```sql
        -- Table is ordered by (postcode, addr1, addr2).
        -- This ORDER BY price requires a full scan despite the LIMIT.
        SELECT * FROM uk_price_paid ORDER BY price DESC LIMIT 5;
        ```

        **Aggregations:** Queries with `GROUP BY` require a full scan unless you enable ordered aggregation:

        ```sql
        SET optimize_aggregation_in_order = 1;

        SELECT
            postcode,
            avg(price)
        FROM uk_price_paid
        GROUP BY postcode;
        ```

        This setting lets ClickHouse stream aggregation when the `GROUP BY` columns match the table's `ORDER BY`, significantly reducing memory usage and improving speed.
    </Step>

    <Step>
        ### IP filtering in Cloud

        ClickHouse Cloud now allows all traffic by default. While this makes getting started easier, it means web crawlers and bots can reach your service's endpoints, potentially waking it from an idled state and causing unexpected costs.

        To avoid this, explicitly add only the IP addresses or CIDR ranges you actually need to the allowlist and remove the default "allow all" entry. You can manage the allowlist in the ClickHouse Cloud console under your service's **Settings** tab.

        <Tip>
        Configure your IP allowlist early — especially before idling your service — to prevent unwanted traffic from waking it up and incurring charges.
        </Tip>
    </Step>

    <Step>
        ### Read-only tables

        If a replicated table suddenly becomes read-only, it has most likely lost its connection to ClickHouse Keeper (or ZooKeeper).

        Check Keeper health:

        ```sql
        SELECT * FROM system.zookeeper WHERE path = '/';
        ```

        **Common causes:**

        - Under-resourced Keeper nodes — Keeper should run on dedicated hardware with sufficient memory.
        - Co-hosting Keeper and ClickHouse on the same machine — they compete for CPU and I/O.

        <Note>
        ClickHouse Cloud manages Keeper automatically, so this issue applies mainly to self-managed deployments.
        </Note>
    </Step>

    <Step>
        ### Memory limit exceeded

        Large queries can exceed available memory, producing `Memory limit exceeded` errors. ClickHouse provides several settings to spill intermediate data to disk instead of failing.

        **For aggregations and sorting:**

        ```sql
        -- Spill GROUP BY state to disk when it exceeds 10 GB in memory
        SET max_bytes_before_external_group_by = 10000000000;

        -- Spill ORDER BY to disk when it exceeds 10 GB in memory
        SET max_bytes_before_external_sort = 10000000000;
        ```

        **For JOINs**, choose the right algorithm:

        | Algorithm | When to use |
        |---|---|
        | `hash` (default) | Small right-hand table that fits in memory. Place the smaller table on the right side of the `JOIN`. |
        | `partial_merge` | Right-hand table is too large for memory. Sorts and indexes it into blocks on disk. |
        | `full_sorting_merge` | Both sides are very large. Sorts both to disk. |
        | `auto` | Starts as `hash`, switches to `partial_merge` if memory limits are approached. |

        ```sql
        SET join_algorithm = 'auto';
        ```

        In multi-user environments, use [quotas and query complexity settings](/docs/en/operations/quotas) to prevent a single query from consuming all resources.
    </Step>

    <Step>
        ### Materialized view pitfalls

        Materialized views are insert triggers — they transform data as it arrives and write the results to a target table. They do **not** react to merges, partition drops, or mutations on the source table.

        **Common mistakes:**

        - **Too many views:** More than ~50 materialized views on a single table slows inserts and creates merge pressure. Consolidate where possible.
        - **Column mismatches:** The `ORDER BY` in the target table must align with the `GROUP BY` in the view's `SELECT`. Column names must match the destination table — use aliases.
        - **Expensive state functions:** Quantile state computations (`quantileState`, `quantileTDigestState`) are CPU-intensive. Use them sparingly.
        - **Source table changes:** If you alter the source table's schema, attached materialized views are not updated automatically. You must manually re-create or adjust them.
    </Step>

    <Step>
        ### Experimental features in production

        ClickHouse marks experimental features with settings like `allow_experimental_*`. These features require explicit opt-in:

        ```sql
        SET allow_experimental_lightweight_delete = 1;
        ```

        Experimental features may change behaviour, have bugs, or be removed entirely in future releases. Try them for feedback, but do not build production workflows around them until they are marked as production-ready in the release notes.
    </Step>

</Steps>
